01 · The model

Each folder is a Person Group, and each folder has a code

The proposed folder structure matches the DSS model. The difference is that DSS doesn't identify a folder by its name. It uses a numeric code that it generates itself, called the orgCode.

02 · Folder lifecycle

From creating the folder to a registered person

Five steps, each labeled with who makes the call. The proposal further down keeps the first two on our side.

Create the SOC folder

Our team

Sends the parent folder, the name and which access profiles can see the folder. DSS replies with the new orgCode.

POST /obms/api/v1.1/acs/person-group
{ "parentOrgCode": "001001001",
  "orgName": "INTEGRACAO",
  "roleIds": ["1","2","3","5","6"] }

→ { "orgCode": "001001001003" }

Tag it as an integration folder

Our team

A second call stores SPX's own SOC code in the associateId field. That lets SPX find the folder by a code it controls, without relying on the folder name.

PUT /obms/api/v1.1/acs/person-group/001001001003
{ "orgName": "INTEGRACAO",
  "sourceType": 3,
  "associateId": "SOC-ES2" }

SPX looks up the codes

SPX

One call returns the full tree: code, name, parent folder, headcount and associateId. SPX keeps the pair SOC code → orgCode.

GET /obms/api/v1.1/acs/person-group/list

Register the person

SPX

Each person is registered with the orgCode of their SOC's integration folder. Updates and deletions also go through the API, and DSS publishes every change to a message queue.

POST /obms/api/v1.1/acs/person

Delete, when needed

Our team

Folder deletion is asynchronous. The API confirms right away and the folder leaves the tree a few seconds later. Wait for one deletion to finish before sending the next.

DELETE /obms/api/v1.1/acs/person-group/{orgCode}?mode=1
03 · What we tested

Every call was run on our 8.6 server first

The documentation covers DSS 8.8 and our server runs 8.6, so nothing here is assumed. Each row was executed on 4 Nov 2026 against a test folder that was created and then deleted.

CallResultWhat we found
GET /person-group/list Works Returns the full tree with code, name, parent folder and headcount.
GET /person-group/{orgCode} Works Folder details, including the profiles that can see it.
POST /person-group Needs a fix Requires an access-profile field (roleIds) that the documentation leaves out. Without it, the error is generic.
POST with sourceType: 3 Rejected Error 141088: a third-party folder can't be created directly on the platform.
POST with associateId Ignored Returns success but stores an empty value. It only saves on edit.
PUT /person-group/{orgCode} Works Accepts associateId and sourceType: 3, and can rename the folder.
DELETE ?mode=1 Works Confirms immediately, removes shortly after. A second deletion sent while the first is running is rejected.
mode=1 vs mode=2 Open Identical on an empty folder. The difference only shows with people inside, which needs a pilot SOC.
04 · Three gotchas

What the documentation doesn't say

None of these blocks the integration. Each would have cost days of back-and-forth if we had found it later.

Missing field

Creating a folder requires access profiles

Every folder carries the list of DSS user profiles that can see it. The documentation doesn't mention this field, and without it DSS only replies “Failed”. These profiles are our internal permissions, so SPX shouldn't have to manage them.

Rejected

A third-party folder can't be created as third-party

DSS blocks tagging a folder as externally sourced at creation time. The same tag is accepted afterwards, as an edit.

Silent

The SOC code only saves on edit

At creation, DSS accepts the SOC code, replies “Success” and stores nothing. It only saves through an edit, so creating an integration folder takes two calls.

05 · Proposal

Who creates the folders

Both options work. The difference is how much of the internal DSS setup SPX has to know about.

Option A: our team creates them

Recommended
  • We set up each SOC's folder and hand over the orgCode, ready to use.
  • SPX doesn't deal with permission profiles or the two-call creation.
  • SPX uses the orgCode as its key. It doesn't change when a folder is renamed.
  • SPX's side of the integration comes down to two calls: read the folder list and register people.

Option B: SPX creates them

Viable
  • We first agree on which profiles go into each folder.
  • Each new folder takes two calls: create, then tag.
  • Any new profile in DSS means a change to SPX's code.
  • Makes sense if new SOCs are added often and in volume.

06 · Operations

Four things the SPX technical team needs to know

Address: hostname, not IP

The connection is HTTPS on port 443. If SPX points at an IP and the server's address changes, the integration breaks with no warning, so a hostname is safer. Plain HTTP on port 80 only works if SPX's server IP is added to an allowlist on the DSS server.

Token authentication

Token with automatic renewal every ~20 seconds. It's already implemented and tested on our side. SPX only needs to plan for the renewal.

Deletion is asynchronous

The API confirms before the work is done, so “success” doesn't mean “deleted”. Check the folder list to be sure. A second deletion sent while one is still running is rejected, so space them out or retry.

Deleted codes are never reused

If a folder is deleted and recreated, it gets a new orgCode. SPX should never predict codes, and should refresh the folder list regularly or whenever a registration fails with a missing folder.
